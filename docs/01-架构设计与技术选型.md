# 亿网通IT运维监控管理平台
## 第 1 步：项目架构设计（含技术选型方案）

> 文档状态：待确认
> 编写日期：2026-09-21
> 面向场景：政企弱电 / 系统集成项目的网络设备、服务器、信创主机统一监控 + IT资产台账 + 可视化大屏 + 多渠道告警

---

## 一、项目定位与设计原则

平台要解决的四个核心问题：

| 问题 | 设计回答 |
|---|---|
| 设备品牌杂、协议杂（华为/H3C/Windows/Linux/信创） | 采集层插件化：`Collector` 抽象基类 + 工厂注册，新增厂商 = 新增一个类，不动主流程 |
| 200 台并发采集不能卡死 Web | 采集线程池与 FastAPI 主进程解耦，采集结果落库后由 API 只读查询 |
| 告警瞬时抖动误报、消息轰炸 | 连续 N 次超标才触发（N 可配）+ 滞回恢复（连续 M 次正常才恢复）+ 指纹收敛窗口 |
| 先 SQLite 后 MySQL | 全程 SQLAlchemy 2.0 ORM，仅改 `DATABASE_URL` 即可迁移，禁止裸写 SQLite 方言 SQL |

**四条硬性原则（贯穿全部代码）**

1. **采集失败隔离**：单台设备采集异常必须被 `try/except` 吞掉并写采集日志，绝不冒泡到调度线程。
2. **配置驱动**：SNMP 团体字、SSH 账号、WinRM 账号、Ping 周期、告警阈值一律入库可配，不硬编码。
3. **低耦合扩展**：采集器、告警渠道、指标解析器全部走**注册器模式**（Registry），新增不改旧代码。
4. **中文注释**：每个模块/类/关键函数写清楚"为什么这么做"，不是"这行做了什么"。

## 二、关键技术选型方案（先选型，后编码）

### 选型 1：并发采集模型 ⭐ 核心

| 方案 | 说明 | 结论 |
|---|---|---|
| A. APScheduler + ThreadPoolExecutor（**推荐**） | 采集全是网络 IO（SNMP/SSH/WinRM/ICMP），GIL 在 IO 等待时释放，线程池足够；零外部依赖，一键部署 | ✅ 采用 |
| B. Celery + Redis | 功能强，但引入 Redis/消息中间件，政企内网一键部署成本高 | ❌ 过重 |
| C. 纯 asyncio | pysnmp 有 asyncio 支持，但 paramiko/netmiko/wmi/pywinrm 均为同步阻塞库，需 `run_in_executor` 包装，收益不明显 | ❌ 生态不齐 |

**落地参数**：`ThreadPoolExecutor(max_workers=60)`
- 200 台设备 ÷ 60 并发 ≈ 4 批，单批超时 10s → 全量轮询 < 60s，满足分钟级采集周期。
- 每台设备独立 `future`，超时单独控制，**慢设备不拖累整批**。
- 同设备**加锁防重入**：上一轮未结束则跳过本轮（避免 SSH 慢设备堆积）。

### 选型 2：数据库访问层

`SQLAlchemy 2.0` + `databases`？不用。直接用 **SQLAlchemy 2.0 ORM（同步 Session）+ 线程池**即可：
- 采集线程用 `scoped_session`（线程本地会话），天然线程安全。
- SQLite 开启 `WAL 模式` + `busy_timeout=5000`，解决多写并发锁冲突。
- MySQL 迁移只需改 `DATABASE_URL`，配合 `pymysql` 驱动。**注意**：迁移时避免使用 SQLite 特有函数（如 `strftime`），统一用 Python 侧时间处理。

### 选型 3：时序指标存储

指标分两处写，这是性能关键：

| 表 | 作用 | 写入策略 |
|---|---|---|
| `metric_latest` | 每台设备每个指标的**最新值**（大屏秒级刷新读这里） | UPSERT（有则更新，无则插入），行数 = 设备数 × 指标数，可控 |
| `metric_sample` | 历史采样明细（画曲线） | 只追加；**降采样保留策略**：7 天原始 → 30 天按 5 分钟聚合 → 90 天按小时聚合，由清理定时任务执行 |

> 理由：大屏若直接扫 `metric_sample` 全表，200 台设备 × 每月百万行会拖垮 SQLite。冷热分离是刚需。

### 选型 4：前端大屏形态

| 方案 | 说明 | 结论 |
|---|---|---|
| A. FastAPI 挂载静态目录 + Vue3(CDN) + ECharts(CDN)，零构建 | 双击启动脚本即可用，无 npm 环境也能跑，符合"Windows/Linux 一键部署" | ✅ 默认交付 |
| B. Vite 工程化（npm build → dist） | 工程规范好，但客户现场需 Node 环境 | ⭕ 后续可选，代码目录预留 `web/` 结构 |

采用 **A 方案**：所有页面由 FastAPI 的 `StaticFiles` 托管，Vue3 `createApp` + ECharts，组件化拆分为 `设备总览 / 资源运行 / 网络流量 / 容量视图 / 告警滚动` 五个卡片，轮询 `setInterval` 自动刷新。
> 说明：CDN 依赖在政企内网可能不可用，因此**所有 JS 库会本地化到 `web/static/vendor/`**（第 6 步交付时下载打包），保证完全离线可用。

### 选型 5：告警引擎

- **触发策略**：每个指标规则配 `duration_n`（连续超标次数）。采集器写库后调用 `AlarmEvaluator.evaluate(device_id, metric_key, value)`，内部维护该规则的连续计数器（内存 + 落库 `alert_rule_state` 防重启丢失）。
- **滞回恢复**：连续 `recovery_n` 次正常才置为已恢复，避免阈值边缘反复抖动。
- **收敛**：告警指纹 `fingerprint = md5(device_id + rule_id)`，窗口 `converge_window`（默认 300s）内同指纹只发首次 + 末尾汇总，或按 `converge_max`（默认 3 条）限流。
- **通知**：`Notifier` 抽象基类 + 注册器，`EmailChannel / WeComChannel / DingTalkChannel / WeChatChannel` 四个实现，异步线程池发送，失败重试 2 次并写告警日志。

### 选型 6：认证与权限

- JWT（`python-jose`）+ `passlib[bcrypt]` 密码哈希。
- 两角色：`admin`（全权限）、`viewer`（只读，可确认告警）。所有写接口用 `Depends(require_role("admin"))` 守卫。

## 三、总体架构分层

```
┌──────────────────────────────────────────────────────────────┐
│  展示层  Presentation                                          │
│  大屏 dashboard.html(Vue3+ECharts) │ 后台管理 admin.html      │
│  设备管理 │ 资产管理 │ 指标曲线 │ 告警中心 │ 系统配置          │
└──────────────────────────────────────────────────────────────┘
                            ↓ HTTP / JSON (REST)
┌──────────────────────────────────────────────────────────────┐
│  接口层  FastAPI                                               │
│  /api/auth  /api/devices  /api/assets  /api/metrics           │
│  /api/alerts  /api/dashboard  /api/system  /api/logs          │
│  统一响应封装 │ 全局异常 │ JWT鉴权 │ RBAC守卫                  │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  业务层  Service                                               │
│  DeviceService │ AssetService │ MetricService                │
│  AlarmService(评估/收敛/通知) │ DashboardService(聚合统计)     │
└──────────────────────────────────────────────────────────────┘
        ↑                                        ↓
┌──────────────────────┐        ┌──────────────────────────────┐
│  调度层  Scheduler    │───────▶│  采集层  Collector(插件化)    │
│  APScheduler          │        │  SNMP │ SSH │ WinRM │ ICMP   │
│  轮询/定时/周期任务    │        │  厂商适配: 华为/H3C/Windows  │
└──────────────────────┘        └──────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  数据层  SQLAlchemy 2.0 + SQLite(可迁 MySQL)                   │
│  设备/资产/规则/告警/指标(冷热分离)/日志/用户/配置              │
└──────────────────────────────────────────────────────────────┘
```

**分层职责边界（严格遵守，禁止跨层调用）**
- 接口层只做参数校验 + 调 Service + 序列化，**不写业务逻辑、不直接写 SQL**。
- Service 不感知 HTTP（不出现 `Request` 对象），便于单测与复用。
- 采集层只产出**归一化指标字典**，不直接写业务表，交 `MetricService` 统一入库 + 触发告警评估。

## 四、数据流图

### 4.1 采集数据流（主链路）

```
[APScheduler 触发]
      │  按 device.collect_interval 生成任务
      ▼
[采集调度器 Scheduler.dispatch]
      │  1. 过滤: 启用? 周期内? 上一轮未完成?
      │  2. 提交 ThreadPoolExecutor(60)
      ▼
[采集器工厂 CollectorFactory.get(protocol)]
      │  snmp → SnmpCollector(pysnmp v2c/v3)
      │  ssh  → SshCollector(netmiko: huawei/hp_comware)
      │  winrm→ WinRmCollector(pywinrm)
      │  icmp → IcmpCollector(长Ping: 丢包率/延迟)
      ▼
[厂商解析器 Parser]  ← 华为/H3C 命令差异在此消化
      │  输出归一化: {"cpu_usage": 37.5, "mem_usage": 62.1, ...}
      ▼
[MetricService.ingest(device_id, metrics, ts)]
      ├─▶ metric_latest  UPSERT        (大屏实时读)
      ├─▶ metric_sample  INSERT        (历史曲线)
      └─▶ AlarmEvaluator.evaluate(...) (同步评估)
                │
                ▼
         [告警状态机 + 收敛器]
                │ 连续N次超标 ─▶ 生成 alert_event
                ▼
         [Notifier 多渠道推送] ─▶ 邮件/企微/钉钉/微信
      │
      └─▶ collect_log (成功/失败/耗时 全部落日志)
```

### 4.2 告警状态机

```
        ┌──────────┐
        │  NORMAL  │  正常
        └────┬─────┘
   连续N次超标 │ (计数器 counter++ >= duration_n)
              ▼
        ┌──────────┐   收敛窗口内同指纹   ┌────────────┐
        │ FIRING   │ ──────────────────▶ │ CONVERGED  │ 合并计数，不重复推送
        │ 告警中    │                     │ 已收敛      │
        └────┬─────┘                     └────────────┘
  连续M次正常 │ (滞回 recovery_n)
              ▼
        ┌──────────┐
        │ RECOVERED│  已恢复(发恢复通知) → 回 NORMAL
        └──────────┘

    人工确认: ack (ACKED) ── 抑制后续推送，设备恢复后自动关闭
```

### 4.3 大屏数据流

```
Vue3 页面 setInterval(15s)
   │  并发请求
   ├─▶ GET /api/dashboard/overview     总览: 在线/离线/资产/告警分级统计
   ├─▶ GET /api/dashboard/resource     资源: CPU/内存均值 + 磁盘趋势
   ├─▶ GET /api/dashboard/network      网络: 端口流量TOP10 + 延迟/丢包
   ├─▶ GET /api/dashboard/capacity     容量: 磁盘占用饼图 + 维保到期预警
   └─▶ GET /api/alerts/latest?limit=20 告警滚动字幕
   │
   ▼
DashboardService 聚合查询
   │  优先读 metric_latest(热表) 做实时态
   │  趋势类读 metric_sample(按时间桶聚合)
   ▼
ECharts setOption 局部刷新(不销毁实例)
```

## 六、非功能需求的落地设计

| 需求 | 落地方案 |
|---|---|
| 200 台并发、不阻塞 Web | 采集在独立线程池；FastAPI 用 `ThreadPoolExecutor` 跑同步 ORM（默认行为），接口只做读；SQLite 开 WAL |
| 系统/采集/告警三类日志 | `logger.py` 定义三个 logger：`system` / `collect` / `alarm`，按天切分文件；同时 `collect_log`、`alarm_log` 落库供页面查询 |
| 采集失败不影响其他设备 | 每个采集任务 `try/except Exception` + `finally` 释放设备锁；失败写 `collect_log` 并累加 `device.fail_count`，连续失败 N 次自动标记设备异常但不删除任务 |
| 扩展性 | 采集器/解析器/告警渠道三处注册器 + 抽象基类；指标键(`metric_key`)字典化配置，新增指标不改表结构 |
| 一键部署 | `scripts/start.sh` / `start.bat` 自动建 venv → 装依赖 → 初始化库表 → 灌演示数据 → 启动 Uvicorn；Windows 下 WinRM 采集自动启用 |

## 七、风险与取舍说明

1. **SQLite 写并发上限**：200 台 × 每分钟 ≈ 200 写/分钟，WAL 模式可承受；若超过 500 台或采集周期 < 30s，建议直接切 MySQL（配置级切换，代码零改动）。
2. **SNMP Walk 开销**：端口流量采集走 `ifHCInOctets/ifHCOutOctets` 批量 Get（一次请求多 OID），不做逐端口 Walk，降低设备 CPU 压力。
3. **SSH 采集慢**：SSH 仅用于"设备版本/接口信息/日志"等低频信息（默认 10 分钟级），不参与秒级指标；高频指标走 SNMP/Ping。
4. **信创主机**：本质是 Linux（麒麟/统信），走 SSH + 标准 `top/free/df` 命令解析，与 Linux 服务器共用采集器，通过 `os_type` 字段区分。
