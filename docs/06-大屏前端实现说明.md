### 1.2 为什么前端依赖必须本地化（不能走 CDN）

```
web/static/vendor/
├── echarts.min.js      1,030,855 字节
└── vue.global.prod.js    146,843 字节
```

**这是本项目的硬性交付约束，不是"顺手优化"**：

政企客户的监控大屏部署在**内网业务区甚至专网**，服务器通常没有出网权限。若页面里写
`<script src="https://cdn.jsdelivr.net/npm/echarts@5/dist/echarts.min.js">`，交付到现场的结果就是
**一张纯黑页面 + 满屏控制台报错**，而现场工程师的第一反应会是"这套平台有问题"。

因此：

- 两个库**下载后入库到 `web/static/vendor/`**（由 FastAPI 以 `/static` 挂载托管）
- `web/dashboard.html` 与 `web/admin.html` **不得出现任何 `http://` / `https://` 形式的脚本、样式、字体外链**
- 后续若要做巡检（把 `static_audit` 的检查项扩展到前端），这条可以直接变成一条静态规则

### 1.3 页面导航结构

```
http://<host>:<port>/            →  可视化大屏   web/dashboard.html
http://<host>:<port>/admin       →  后台管理     web/admin.html
```

两个页面**共用同一个 token**（`localStorage.itsm_token`），管理员登录后点"进入后台管理"不需要二次登录；
反过来 viewer 登录后进入后台也能自动带入身份，只是**写操作按钮按后端返回的权限隐藏**。

## 二、前端实现的六个关键取舍

### 2.1 取舍一：大屏用「设计基准 1920×1080 + scale 缩放」，不做响应式

```js
const DESIGN_W = 1920, DESIGN_H = 1080;
const s = Math.min(innerWidth / DESIGN_W, innerHeight / DESIGN_H);
stage.style.transform = `scale(${s})`;
```

**为什么不做响应式：** 大屏的用途是**挂在值班室墙上 7×24 小时显示**，屏幕尺寸是已知的、固定的
（1920×1080 或 3840×2160）。做响应式的代价是：

- 元素数量多（7 张 KPI 卡 + 3 个图表 + 12 格设备矩阵 + 滚动字幕），断点会指数级膨胀
- 一旦某个断点没调好，投屏时会出现"图表挤成一条"，而这恰恰是最不能出错的场景

采用 `scale` 的好处是**版式绝对可控**：1920×1080 下调好的样子，投到 4K 屏上就是等比例放大，
不会有一像素错位。代价是在超宽屏上左右会有黑边 —— 对大屏场景而言，黑边远好过错位。

### 2.2 取舍二：前端零业务常量（配色 / 阈值 / 中文标签全部来自后端）

这条是本项目前后端分工的核心约定：

| 内容 | 传统做法（前端写死） | 本项目做法（后端下发） |
| --- | --- | --- |
| 卡片是"正常"还是"告警"色 | 前端 `if (value > 80) red` | 后端返回 `level` + `color` |
| 设备状态灯颜色 | 前端 `{online:'#0f0', offline:'#f00'}` | 后端返回 `status` + `status_text` + 色值 |
| 告警级别阈值（TOP 榜绿/黄/红） | 前端写 `>90 危险` | 后端 `_RANK_LEVELS` 一张表统一下发 |
| 设备类型中文名 | 前端 map | 后端 `type_text` |
| 厂商中文名 | 前端 map | 后端 `vendor_text` |

**为什么值得这么较真：** 阈值和配色是典型的"同一件事两处定义"。
一旦前端有一份，调整告警阈值时就必须**同时改后端判定逻辑和前端显示阈值**，
而这两处分居两个文件、改一处不报错、失效点离改动点很远 ——
结果就是"告警已经报了，但大屏上还是绿色"。这个缺陷族在第 5 步已经出现过 4 个实例（见 `05-告警推送实现说明.md`），
这里从一开始就不给它机会。

前端因此只保留**布局类主题色**（背景、面板边框、品牌色），业务色一律由后端给。

### 2.3 取舍三：首屏走 `/bundle` 整屏打包，之后按不同节奏分别刷新

见下一节的刷新节奏表。**反对"拼图式加载"**：

如果首屏并发打 5 个请求各自渲染，一旦其中一个失败，屏幕上就是"三块有数据、一块空白"——
值班的人无法判断这是"真的没数据"还是"接口挂了"，而在监控场景里，
**无法判断 = 只能当故障处理 = 白跑一趟机房**。

整屏打包让失败模式收敛成两种：**要么整屏可用，要么整屏报同一个错**（并可整体重试）。

### 2.4 取舍四：设备状态是「四态」而不是库里的三态

```python
def _device_status_code(device) -> str:
    if not device.enabled:
        return "disabled"          # ← 显示层独有的第四态
    return device.online_status or "unknown"
```

`mon_device.online_status` 在库里只有三态（online / offline / unknown）。
但设备还有 `enabled` 字段表示"是否参与采集"。若大屏直接把 `online_status` 画出来，
一台**被人工停用采集**的设备因为最后一次采集结果留着 `online`，会被显示成"在线"。

这在演示环境看不出来（演示库里没有停用设备），但在客户现场一定会遇到
（比如设备下架待报废、或某个分支点长期无人值守先停掉）。
后果比"看起来故障"更糟：**它让大屏对真实故障失去可信度**。

### 2.5 取舍五：告警趋势的分桶在 Python 里做

```python
# 不用 SQL 的 strftime('%Y-%m-%d %H') —— 那是 SQLite 方言
# 不用 SQL 的 DATE_FORMAT(created_at,'%Y-%m-%d %H') —— 那是 MySQL 方言
bucket = ts.strftime("%Y-%m-%d %H:00")     # Python 里按小时分桶
```

原因在第 2 步就定下了：**SQLite ↔ MySQL 只改 `DATABASE_URL`**。
一旦在 SQL 里用了方言函数，这条约定就被破坏，而且**在 SQLite 上完全测不出来** ——
等到现场切 MySQL 才发现趋势图报错，属于典型的"迁移时才炸的雷"。

### 2.6 取舍六：401 弹登录浮层，而不是弹红条或者跳登录页

大屏是 7×24 挂着的，`ACCESS_TOKEN_EXPIRE_MINUTES` 默认 12 小时（一个班次），
**token 到期是必然事件而不是异常**。处理方式必须满足：

- 不能整屏白掉（值班的人会以为大屏崩了）
- 不能跳去登录页（大屏机器上通常没人操作、而且在墙上）
- 要能就地输密码续期，且无需刷新页面（保留断开前的最后画面）

实现：捕获 401 → 在原画面上盖一层半透明浮层，提示"登录已过期，请重新登录"，
重新登录成功后**直接恢复原有定时器**，不做 `location.reload()`。

## 三、大屏数据接口（6 个）

统一前缀 `/api/v1/dashboard`，全部需要登录（`get_current_user`）。

### 3.1 刷新节奏表（前后端约定）

| 接口 | 内容 | 建议间隔 | 理由 |
| --- | --- | --- | --- |
| `GET /bundle` | 整屏（总览+设备+趋势+分布） | **首屏一次** | 避免拼图式逐块出现 |
| `GET /overview` | 顶部 KPI + 状态分布 | 10 秒 | 变化最快，要"看起来是实时的" |
| `GET /devices` | 设备状态灯矩阵 | 30 秒 | 设备状态变化远慢于指标 |
| `GET /rank` | TOP N 排行榜 | 30 秒 | 与设备矩阵同步 |
| `GET /alert-trend` | 告警趋势 | 60 秒 | 按小时分桶，10 秒刷毫无意义 |
| `GET /distribution` | 分布类环形图 | 300 秒 | 台账属性，几乎不变 |

节奏由前端统一调度，后端不限制 —— 但表里把理由写清楚，
后续调优时有依据，而不是"看着不爽就改成 5 秒"。

### 3.2 接口明细

| 接口 | 参数 | 返回要点 |
| --- | --- | --- |
| `/overview` | — | 7 张 KPI 卡（每张带 `level`/`color`）+ 状态分布 + `data_fresh_at` |
| `/devices` | `limit`（1–1000，默认 200） | 四态 `status` + `status_text` + CPU/内存/延迟实时值 |
| `/alert-trend` | `hours`（1–336，默认 24） | 按小时分桶的告警发生数 / 恢复数 |
| `/rank` | `metric_key`、`limit`（1–50） | TOP N；端口类指标按设备取最大值并在 key 里带端口名 |
| `/distribution` | — | 设备类型 / 资产状态 / 告警级别 / 厂商 四组分布，全部中文 |
| `/bundle` | `hours` | `{overview, devices, trend, distribution}` |

### 3.3 「数据新鲜度」为什么单独返回

`kpi_summary()` 除了业务数据还返回 `data_fresh_at`（最近一次成功采集的时间）。

**这是专门给运维准备的"平台自监控"**：大屏在最显眼的位置显示"数据截止 16:31:47"。
如果某天采集调度挂了，大屏上的所有数字会**停留在最后一次的正确值**——
看起来一切正常，实际上已经 6 小时没采集了。有了这个时间戳，值班的人一眼就能发现。

同理还有**采集健康度**：近 24h 采集次数、成功率、平均耗时三项，全部进 KPI 区。

### 4.1 版面分区

```
┌────────────────────────────────────────────────────────────────┐

├────────────────────────────────────────────────────────────────┤
│ KPI 区（7 列）：设备总数 在线 离线 未恢复告警 今日新增 采集成功率 资产 │
├──────────────┬──────────────────────────────┬──────────────────┤
│ 设备类型环图 │ 告警趋势（柱 + 折线）         │ TOP N 排行横条图 │
│   400px      │        1fr                   │     460px        │
├──────────────┴──────────────────────────────┴──────────────────┤
│ 设备状态灯矩阵（8 列网格，超出可视区自动上滚 @ 60px/s）         │
├────────────────────────────────────────────────────────────────┤
│ 底栏：最新告警滚动字幕 │ 数据新鲜度 / 采集健康度                 │
└────────────────────────────────────────────────────────────────┘
```

### 4.2 三个图表

| 图表 | 类型 | 数据来源 | 要点 |
| --- | --- | --- | --- |
| 设备类型分布 | ECharts 环形图 | `/distribution` | 色板由后端 `DEVICE_TYPE_COLOR` 下发，10 色循环 |
| 告警趋势 | 柱状图 + 折线叠加 | `/alert-trend` | 柱=发生数，折线=恢复数；没有"发生/恢复"的分野就看不出趋势健康度 |
| TOP N 排行 | 横向条形图 | `/rank` | 指标下拉从 `/metrics/catalog` 动态填充；绿/黄/红由后端 `_RANK_LEVELS` 判定 |

**排行指标的空数据要给出"为什么空"**：演示库里没有端口流量数据（`if_in_rate`），
页面显示的是"暂无足够数据"而不是一个空框 —— 否则值班的人会以为是采集出问题了，
实际上只是这条规则没配采集项。

### 4.3 设备矩阵的滚动

设备数量少于 2 行时不滚动且**垂直居中**（避免下方大片留白）；
超过可视区才启动 CSS 动画滚动，速度按 60px/秒换算成 `--scroll-dur`，
保证不同设备数量下**视觉速度一致**（而不是"设备越多滚越快"）。

### 4.4 容错：任一次刷新失败不清屏

```js
const guard = async (fn, label) => {
  try { await fn(); }
  catch (e) { toast(`${label} 刷新失败：${e.message}`); }   // 只提示，不清数据
};
```

大屏最忌讳的行为是**因为一次网络抖动把整屏清空**。
刷新失败时保留上一次的数据 + 右下角 toast，比"显示 loading 然后变空"安全得多。

单文件 Vue3，8 个功能视图：

| 告警中心 | 列表、详情、**处理时间线**、**推送记录**、单条确认、批量确认、按级别/状态筛选 |

### 5.1 权限在界面上的落地

前端不做鉴权（鉴权在后端），但**按角色隐藏写操作按钮**：

> **注**：本项目实际只有 **admin / viewer 两个角色**（`VALID_ROLES = {"admin","viewer"}`），
> 下表按角色列出；需求书中提到的"操作员"档由 viewer 承担（可确认告警）。

| 角色 | 能看到 |
| --- | --- |
| admin | 全部：新增/编辑/删除/启停/配置修改/用户管理 |
| viewer | 只读；**告警确认可用**（值班要能认领告警） |

管理员视角验证结果：`新增设备` 可见、`编辑`/`停用`/`删除` 可见（`admin-devices.png`）；
viewer 视角验证结果：`新增设备`/`编辑`/`停用`/`删除` 全部不可见，但告警中心的 `确认`/`详情`/`时间线`/`推送` 可用。

### 5.2 「推送记录」是排障第一入口

告警中心每行除了"详情 / 时间线 / 确认"，还有 **推送** 按钮，展示该事件各渠道的推送结果：

| 看到的现象 | 结论 | 下一步 |
| --- | --- | --- |
| 有记录，`success=true` | 平台已送出 | 问题在接收端（企微机器人是否被移出群、邮件是否被拦） |
| 有记录，`success=false` | 平台侧失败 | 看 `error_msg`：凭据过期 / 网络不通 / 频率限制 |
| **无记录** | 没走到推送环节 | 检查规则是否被静默、是否命中收敛限额（`/alerts/rules` 的静默期） |

**这个按钮专门为"为什么没收到告警"这个问题准备的** —— 这是运维最常问、最难一句话回答的问题，
以前只能去翻服务器日志，现在在界面上两次点击就能定性。

## 六、本步发现并修复的问题

### 6.1 厂商分布显示英文编码值（真实缺陷）

**现象：** 大屏"厂商分布"环形图显示为 `sangfor / hikvision / kylin / uos`。

**根因：** `DeviceOut` 里 `type_text` / `protocol_text` / `online_text` 三张映射表都有，
唯独 `vendor` 没有 —— 因为 `mon_device.vendor` 是一个**自由字符串**（不做枚举校验），
写映射表时容易漏掉它：类型转换逻辑看着"已经覆盖完了"。

**为什么这张图特别重要：** 它正是用来看**信创适配覆盖了哪些国产品牌**的
（麒麟、统信、鲲鹏、海光…）。显示成英文缩写，客户汇报时完全没法用。

**修法：** `app/schemas/device.py` 新增 `VENDOR_TEXT`（18 个厂商）
+ `DeviceOut.vendor_text` computed_field（小写查表，**未登记的厂商原样透出**而不是显示"未知"）；
`dashboard_service.distribution()` 传入该表并启用 `lower_key=True`
——现场录设备时完全可能写成 `Huawei` / `HUAWEI`，必须归一化后再查。

修复后实测：`华为 / 深信服 / 海康威视 / 麒麟 / 统信 / 新华三`。

### 6.2 后台侧栏与主区上下堆叠（浏览器验证发现）

**现象：** 首次截图 `admin-devices.png` 显示侧栏在上方、内容区被挤到下方且压扁。

**根因：** `aside` / `main` 是 `#app` 容器的子元素，而 `display:flex` 写在 `body` 上 ——
`#app` 作为唯一的 flex item 撑满高度，但**它内部的两个兄弟仍是普通块级流**。
这是 Vue 单文件页最常见的坑之一：`<body><div id="app"><aside/><main/></div></body>`
比直觉上多了一层。

**修法：** flex 容器下移到 `#app`。

### 6.3 设备矩阵下方留白（视觉细节）

设备只有 12 台时排满不到两行，矩阵区底部出现大块空白且整体偏上。
改为 `align-content:center`（不足两行时）+ 单元格 `min-height` 兜底。

### 6.4 关于启动慢的说明（**不是缺陷**）

本地 `uvicorn` 冷启动约 22 秒，其中 `apscheduler` 15.85s + `pydantic_settings` 5.38s。
用 `cProfile` 定位到根因：`apscheduler.schedulers.base` 导入时调用
`importlib.metadata.entry_points()` 扫描 72 组包元数据，触发 315 次文件读取，
而本开发环境的文件读取经过 WorkBuddy 沙箱的 socket 代理（每次约 52ms）—— 合计 16.2 秒。

**结论：这是开发环境沙箱的 I/O 代理开销，不是产品缺陷。** 正常机器上这个过程远小于 1 秒。
生产部署文档（第 8 步）里会提一句：首次请求慢属正常，warmup 后稳定在毫秒级。
