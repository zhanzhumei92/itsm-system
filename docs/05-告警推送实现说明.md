### 1.2 告警数据流全景

```
  采集任务（第4步，每 60 秒 tick）
        │  写入 metric_latest + metric_sample
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ ① evaluator.evaluate_devices(db, device_ids)                │
  │    对每台设备 × 每条适用规则（专属规则 + 全局规则）           │
  │      ├─ 取指标值：取不到 → 不评估（状态机停在原地）           │
  │      ├─ 超标 → breach_count+1，达 duration_n → 触发          │
  │      └─ 正常 → normal_count+1，达 recovery_n → 恢复          │
  └─────────────────────────────────────────────────────────────┘
        │ 触发/恢复事件（写 alert_event + alarm_log）
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ ② converger.decide(db, *, rule=…, event=…)                  │
  │      a. 静默期？（rule.silence_until）      → 拒发，记 suppressed│
  │      b. 窗口内事件数 ≥ converge_max？（按 **事件** 计数）     │
  │                                            → 拒发，记限流    │
  │      c. 通过 → allowed                                      │
  └─────────────────────────────────────────────────────────────┘
        │ allowed
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ ③ notifier.dispatch(db, event, rule)                        │
  │      先落一条 pending 推送记录（任何时刻可回答"发到哪一步"）  │
  │      再投递给 **独立通知线程池**（8 线程）                    │
  └─────────────────────────────────────────────────────────────┘
        │ 线程池异步
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ ④ notifier._deliver(record_id, channel_key, message)        │
  │      按注册器取渠道 → check(cfg) → send() → 重试 3 次（退避） │
  │      回写 alert_notify_record：success / fail + response_msg │
  └─────────────────────────────────────────────────────────────┘
```

## 二、告警引擎：四个关键取舍

### 2.1 通知必须用**独立线程池**，绝不复用采集线程池

这是本步最重要的一条设计决定，也是唯一一个"做错了会在真实故障中放大灾难"的地方。

`NOTIFY_POOL_SIZE = 8`，与采集线程池（默认 20）物理隔离。若把通知任务投进采集池：

```
机房断电 → 200 台设备全部采集失败
        → 200 条"设备离线"告警 + 200 条"设备恢复"告警（来电后）
        → 400 个通知任务涌入采集线程池（20 线程）
        → 每条推送最长耗时 3 次尝试 × 10 秒超时 + 7 秒退避 ≈ 37 秒
        → 20 个线程被推送任务全部占满，且每个都要占 37 秒
        → 【采集任务本身排不上队】→ 更多设备被判离线 → 更多告警
        → 雪崩：平台在最需要它的时候彻底失去采集能力
```

把推送放出去之后，最坏情况只是"告警发得慢"，采集与判定永远不受影响 ——
**告警系统失灵的代价必须局限在"通知晚到"，而不是"监控停摆"**。

线程数取 8 的依据：单条最长 37 秒、收敛限流（同指纹窗口内最多 3 条）已在前面削掉风暴峰值，
8 条并行足以消化；再大反而会触碰企业微信/钉钉的单应用限流（约 20 条/秒）。

### 2.2 收敛计数按「**告警事件数**」而不是「推送条数」，且不另建计数表

收敛要做的是"同一种故障在窗口内最多提醒几次"。这里的"几次"必须是**事件数**：

- 若按推送条数计：一条事件要推 3 个渠道 → 一次故障就吃掉 3 个名额 →
  "窗口内最多 3 条"变成"窗口内最多 1 次故障"，配置语义与直觉不符。
- 用 `COUNT(DISTINCT event_id)`：一次故障推 4 个渠道只算 1 次，符合"提醒几次"的本意。

**并且直接查 `alert_notify_record`，不额外建一张计数表。** 理由：

1. **天然持久化**：进程重启后窗口计数仍然正确。若用内存计数器，重启会把在途告警
   重新推一遍 —— 而"平台重启后运维被重复告警刷屏"正是收敛要防的事。
2. **口径唯一**：推送记录是"确实发过什么"的事实表，计数与事实同源，
   不需要担心"计数表与事实表对不上"（这又是"同一件事两处定义"的经典坑）。
3. 代价是每次判定多一次聚合查询 —— 该表有 `(channel, created_at)` 与事件索引，
   在 200 台设备量级下可以忽略。

### 2.3 三层防护各管一段，分工不得重叠

| 层 | 位置 | 管什么 | 典型参数 |
| --- | --- | --- | --- |
| 抖动抑制 | evaluator | 单设备指标的**瞬时毛刺** | `duration_n`（连续 3 次超标才算） |
| 滞回恢复 | evaluator | 在阈值附近**反复横跳** | `recovery_n`（连续 2 次正常才算恢复） |
| 总量限流 + 静默 | converger | **跨设备的风暴**与**计划维护窗口** | `converge_window=300s` / `converge_max=3` |

三者解决的是三个不同粒度的问题，**任何一层都不能替代另一层**：
只有 `duration_n` 挡不住"50 台设备同时抖一下"；只有 `converge_max` 又会让
单台设备的持续故障被自己限流掉（真正的故障反而被吞）。

配套的两条硬约束：

- **收敛判定必须发生在创建推送记录之前**。若先建 pending 记录再判定，
  被拒发的记录会留在表里，`COUNT(DISTINCT event_id)` 把它算进窗口，
  占掉本该给后续真实告警的名额 —— 表现为"告警偶尔莫名不发"。
- **先落 pending 再异步发送**。任何时刻数据库都能回答"这条告警发到哪一步了"，
  线程池被重启清空也不会丢线索（下次巡检能看到卡在 pending 的记录）。

### 2.4 取不到指标值时**不评估**（状态机停在原地）

```python
if value is None:
    stats["no_value"] += 1
    continue          # 既不记超标，也不记正常
```

这条看似消极的规则防的是一个很具体的错：

```
设备离线 → ping_latency 不再上报 → 若把"取不到"当成"未超标"
        → 连续 2 轮后判定"延迟告警已恢复"
        → 值班人员看到"设备离线了、延迟告警恢复了"
        → 从此不再相信平台的任何一个数字
```

"没有数据"和"数据正常"是两件事。取不到值时状态机**停在原地**，
告警既不变红也不变绿，直到数据真正回来。

### 2.5 一次故障只报一次：触发后清零 + firing 只判恢复

- 触发时把 `breach_count` 清零：故障持续 3 小时、每秒都在超标，
  也只会在第一次触发一次告警，不会反复触发。
- `firing` 状态只判"是否恢复"，不判"是否再次触发"。
- `acked`（已人工确认）状态**持续超标也不重新触发** ——
  否则运维刚点完确认按钮、又收到一条一模一样的告警，"确认"这个动作就失去意义。
  为此补上了 `alert_rule_state.status` 的 acked 同步（见问题 3）。

## 三、四个通知渠道的实现要点

四个渠道的消息格式完全不同，但**内容必须一致**：同一场故障，邮件里写
"CPU 93% 阈值 85%"、企微里写"CPU 使用率过高"，值班人员会怀疑到底哪个是真的。
所以先由 `AlertMessage` 把告警翻译成与渠道无关的中间体，再由各渠道负责"怎么排版"。

| 渠道 | 关键实现 | 踩过的坑 |
| --- | --- | --- |
| 邮件 `email` | `smtplib`，自动按端口选 SSL(465) / STARTTLS(587)；主题与正文都走 RFC 2047 | 主题含中文会被编码成 `=?utf-8?b?…?=`，断言时**必须解码后**再比对，"能解回原文"才是"不乱码"的定义 |
| 企业微信 `wecom` | 群机器人 webhook，markdown 消息 | webhook 地址里带 key，`_mask_url()` 统一脱敏后才允许进日志与 `response_msg` |
| 钉钉 `dingtalk` | markdown + **加签模式**（HMAC-SHA256(secret, timestamp+"\n"+secret)） | 验签失败要当作**不可重试**：签名错重试 3 次只是白等 7 秒，还会触发钉钉的风控 |
| 微信 `wechat` | 服务号模板消息，`access_token` 带**进程内缓存**（提前 5 分钟过期） | 200 台设备的告警不能每发一条都换一次 token —— 微信接口有每日调用上限 |

两个贯穿所有渠道的约定：

1. **绝不把密钥写进日志或返回值**。告警详情的"推送记录"是运维天天看的页面，
   泄漏概率极高。
2. **"渠道没配好"不是"发送失败"**。`check(cfg)` 未通过时 `retryable=False`，
   notifier 不会浪费 2 次重试与退避等待（否则一条没配 webhook 的告警要占线程 37 秒）。

消息长度统一按**字节**截断（`_truncate`，UTF-8），而不是按字符 ——
企微/钉钉的限制是 4096 / 2048 **字节**，按字符算会让中文消息超限一倍。

## 四、本步发现并修复的问题

### 问题 1（严重）：`converger.decide(db, event, rule)` 参数传反 —— 告警全链路静默失效

**现象**：`rule` 与 `event` 两个位置参数在调用处写反。

**根因**：两者都是 ORM 对象，Python 不会做任何类型检查，位置写反不报错。
传反后 `rule.is_silenced()` 实际作用在 `AlertEvent` 对象上 → `AttributeError` →
被 `dispatch()` 最外层的 `try/except` 捕获 → 只记一条日志。

**后果**：**平台一切正常，但永远没人收到告警**。采集正常、指标正常、事件正常、
日志正常，只有推送这一步静默失败 —— 属于最难查的一类故障，
因为所有"看起来该有输出的地方"都有输出。

**修复**：把签名改成**强制关键字传参**，从结构上消灭这种错误：

```python
def decide(db: Session, *, rule: AlertRule, event: AlertEvent, is_recovery: bool = False):
```

写反了会在第一次调用时立刻 `TypeError`，而不是变成一个被吞掉的异常。
并加回归守卫 `test_位置参数传反会立刻报错`。

**推广到全项目**：凡"两个同类型 ORM 对象作为相邻参数"的函数，都应改用强制关键字传参。

### 问题 2：`METRIC_UNITS` 与 `metric_catalog` 指标单位漂移

**现象**：`app/models/alert.py` 的 `METRIC_UNITS`（告警通知显示单位用）与
`sql/init_data.sql` 的 `metric_catalog.unit` 不一致：

- `METRIC_UNITS` 里写了 `temperature` —— **指标字典里根本不存在这个键**（真名是 `device_temp`）；
- `if_in_util` / `if_out_util` 同样是死条目；
- 反过来，字典里真实存在的 `device_temp`、`if_bandwidth`、`disk_free`、
  `process_count`、`device_uptime`、`mem_used`、`if_in_octets`、`if_out_octets`
  **一个都没有登记**。

**后果**：真正在用的指标没有单位，告警里显示成"温度 78"而不是"温度 78℃"；
死条目则说明当初键名就写错了，一直没人发现。

**修复**：重写单位表与字典严格对齐（20 个有单位的指标全部登记），
并新增**静态检查 6** 双向守住：

- ① 字典里有单位、`METRIC_UNITS` 漏登记 → `units_missing`
- ② `METRIC_UNITS` 登记了字典里不存在的键 → `key_unknown`（死条目）
- ③ 两边都有但值不同 → `unit_mismatch`

**顺带修掉检查器自身的缺陷**：`units_missing` 分支的元组位置错位，
把"应然单位"打印成空串（实际是 `℃`）—— **抓得对、提示错**，
运维会照着错误提示去补一个空单位。现在元组第 2/3 位分别是"应然/实然"。

### 问题 3：`alert_rule_state.status` 的 `acked` 是**死代码**

**现象**：全平台只把 `alert_rule_state.status` 写成 `normal` 和 `firing`，
从不写 `acked`；而评估器里有一段 `if state.status == STATE_ACKED:` 的分支。

**根因**：`ack_event()` 只改了 `alert_event.status`，忘了同步规则运行状态。

**后果**：**"已确认后不再重复告警"这条保证只是恰好成立** ——
它借用了 `firing` 分支的行为，并没有被任何代码显式表达。
风险在于：将来有人给 `firing` 分支加需求（例如"长时间未恢复就再次提醒值班"），
这条保证会在无人察觉的情况下失效 —— 运维刚点完确认又收到同样的告警，
"确认"按钮彻底失去意义。

**修复**：新增 `_mark_rule_state_acked()`，在 `ack_event()` / `batch_ack_events()`
中同步状态；`status` 的三态取值集中成 `RULE_STATE_NORMAL / FIRING / ACKED` 常量，
不再散落字面量。

**教训**：**分支存在但永远走不到，比分支不存在更危险** ——
它会让人以为这条逻辑已经被覆盖了。

### 问题 4：`_truncate` 的字节契约是假的

**现象**：函数注释说"预留 20 字节给截断提示"，而后缀
`\n…（内容过长已截断）` 实际占 **34 字节**（中文 3 字节/字）。

**后果**：截断结果实际是 `limit + 14` 字节。当时没被发现，
是因为 `4014 < 4096`（企微上限）、`2014 < 2048`（钉钉上限）恰好都没超 ——
**函数的契约是假的，只是没人踩到**。换个更严格的渠道（或以后有人调小 limit）就会超限。

**修复**：加 `TRUNCATE_SUFFIX` 类属性，按后缀**真实字节数**预留，
让契约与实现一致；`@staticmethod` 改 `@classmethod` 以引用 `cls.TRUNCATE_SUFFIX`。

**教训**："恰好没超"不等于"正确"。这种"靠巧合成立"的代码，
在参数被改动的那一天会突然失效，而且失效点离改动点很远。

### 问题 5：删除设备漏清 `alert_rule_state`，且设备专属规则静默失效

**现象**：真机验证收尾时发现演示库里有 1 条孤儿状态行
（`alert_rule_state.device_id=22`，而设备 22 早已删除）。
`device_service.delete_device()` 只清理凭据、最新指标、资产绑定和——见下——
而模块文档字符串里明明写着"显式清理：凭据、最新指标、规则状态、维保提醒绑定"。

**根因**：这是"**少写一行 delete**"。不会有异常、不会有日志、语法完全正确；
且它**不影响任何已有设备**，只有恰好复用了 device_id 才会显现。

**后果（为什么必须清）**：

- `alert_event` 用自增 ID 做主键，残留旧事件不污染新设备判断 —— 保留是审计资料；
- `alert_rule_state` 的**业务主键是 `(rule_id, device_id)`，device_id 会被复用**
  （SQLite 的 `INTEGER PRIMARY KEY` 就是 rowid，删掉最大 ID 后再插入会重新拿到它）。
  残留状态行 → **新设备一接入就继承了旧设备的告警状态**：
  旧设备离线时把 `breach_count` 累加到 3、`status` 停在 `firing`，
  新设备第一次采集若同样取不到值，评估器会认为"该设备已处于告警中"，
  **既不触发新告警也不发恢复通知** —— 表现为"新接入的设备坏了但没人知道"。

**顺带发现的第二个问题：设备专属规则的"静默失效"**

`alert_rule.device_id` 指向已删除设备时，规则仍显示"启用中"，
但评估器永远不会为它找到设备 → **规则看着生效、实际永不触发**。
管理员半年后翻出来问"这条规则为什么没报过警"，没有任何线索可查。

两条错路都不行：什么都不做 → 静默失效；跟着设备一起删 → 用户配置不可恢复。
最终选择第三条路：

> **置 `enabled=False` 并清掉它的运行状态** —— 规则还在列表里（可按"已停用"筛出），
> 含义明确、可解释、可恢复；管理员重新接入设备后重新启用即可，不必凭记忆重建。

**顺带发现的第三个问题：ORM 身份映射失效（Core UPDATE 不同步会话）**

清理时最初写的是 `AlertRule.__table__.update()`（纯 Core 语句），
数据库改了、会话里缓存的对象还是旧的 —— 同一请求里紧接着读这条规则会读到
`enabled=True`，"已停用"的判断当场失真。改为 `update(AlertRule)`（ORM 级更新，
自动 `synchronize_session`）后修复。同一函数里原有的
`AssetInfo.__table__.update()` 也有同样问题，一并改掉。

**修复方式：用一个测试消灭这一整族缺陷，而不是修好眼前这一处**

新增 `tests/test_data_hygiene.py`（18 项）与 `scripts/check_orphans.py`（现场巡检工具）：

- 契约清单**唯一定义**在 `scripts/check_orphans.py`（四类：清理 / 解绑 / 保留 / 非引用），
  测试文件 `import` 同一份清单 —— 避免"清单两处维护"这个老问题在工具链上重演；
- 用例从**元数据动态扫描**所有带 `device_id` 的表，要求每张表必须表态，
  再真的建库、真的插数据、真的调 `delete_device`，逐表核对；
- **将来任何人加一张带 `device_id` 的表，这个测试都会失败**，强制他回答"删设备时怎么办"。

已做**变异测试**验证守卫有效：故意把"删掉状态清理"和"换回 Core UPDATE"两个缺陷
注入回去，**7 项用例立刻失败**；还原后 18 项全绿。

**现场库已清理**：演示库中的 1 条孤儿行已用 `python scripts/check_orphans.py --fix` 清除，
复扫 0 项错误（清理前已备份到 `/tmp/itsm.db.bak-*`）。

### 问题 6（工具链）：`pyflakes` 输出 15 条未使用导入，其中一条注释是**假的**

清理时发现 `tests/test_alarm.py` 里写着：

```python
import app.alarm  # noqa: F401 - 导入即触发四个渠道模块注册
```

而 `app/alarm/__init__.py` **只有一行 docstring，什么都不做**。
四个渠道的注册实际发生在 `app/alarm/channels/__init__.py` 末尾的容错导入循环里。
这条注释会让后来者以为"删掉这行渠道就不注册了"，从而在排查
"渠道列表为空"时浪费大量时间在错误的方向上。

**修复**：删掉该导入并把注释改为指向真正的注册入口；
同时把 `alert_service` 里两个**没有任何调用方**的转发（`METRIC_UNITS` /
`PORT_KEY_SEPARATOR`）去掉 —— 转发只会让"单位表到底有几个入口"变得说不清。
现 `pyflakes app/ scripts/ tests/` **零输出**。

另外发现 `PORT_KEY_SEPARATOR` 在 `models/alert.py` 与 `services/metric_service.py`
**各定义了一份** `":"`（又是"同一件事两处定义"），且两处恰好相同所以没出事 ——
但告警模块按基名拆键用模型层那份、指标模块拼端口键用服务层那份，
只改一处就会出现"温度 78"（无单位）且不报错。已改为**单一来源**：
服务层从模型层 `import`（`models` 是下层，方向合法）。
