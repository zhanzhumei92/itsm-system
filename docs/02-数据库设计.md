## 一、设计约定

### 1.1 命名规范

| 对象 | 前缀 | 示例 |
|---|---|---|
| 系统/公用域 | `sys_` | `sys_user`、`sys_config`、`sys_log` |
| 监控域 | `mon_` | `mon_device`、`mon_device_credential` |
| 资产域 | `asset_` | `asset_info`、`asset_maintain_remind` |
| 指标域 | `metric_` | `metric_catalog`、`metric_latest`、`metric_sample` |
| 告警域 | `alert_` | `alert_rule`、`alert_event` |
| 日志域 | `*_log` | `collect_log`、`alarm_log` |

字段统一用**小写下划线**命名；时间字段统一 `_at` 后缀；状态/类型字段统一用**字符串枚举**（可读、便于大屏直接展示），布尔值用 `enabled`/`is_xxx` + 整数 0/1。

### 1.2 为什么不用外键约束

SQLite 默认关闭外键、MySQL 迁移时 `ON DELETE` 行为也有差异，且采集高频写入时外键检查有开销。
**决策：不使用物理外键，全部用业务层维护关联完整性**（删除设备时由 Service 显式清理凭据、指标、告警）。这样 SQLite → MySQL 迁移零改造。关联关系在本文 1.4 节表格中明确列出。

### 1.3 SQLite / MySQL 类型映射（迁移无缝的关键）

| 逻辑类型 | SQLite | MySQL | 说明 |
|---|---|---|---|
| 主键 ID | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT AUTO_INCREMENT` | ORM 统一用 `BigInteger`（自增） |
| 短字符串 | `TEXT` | `VARCHAR(n)` | ORM 用 `String(n)` |
| 长文本 | `TEXT` | `TEXT` | 一致 |
| 数值（指标值） | `REAL` | `DECIMAL(18,4)` | ORM 用 `Float`；百分比/流量用实数 |
| 整数计数 | `INTEGER` | `INT` | 一致 |
| 布尔 | `INTEGER`（0/1） | `TINYINT(1)` | ORM 用 `Boolean` |
| 时间 | `TEXT`（存 `YYYY-MM-DD HH:MM:SS`） | `DATETIME` | ORM 用 `DateTime`，**禁止在 SQL 里写 SQLite 的 `strftime`** |
| JSON | `TEXT` | `JSON` | ORM 用 `Text`，序列化在 Python 侧做 |

> 关键约束：**所有业务 SQL 必须走 ORM，禁止拼接 SQLite 方言函数**，这是"改一个 DATABASE_URL 就迁移"能成立的前提。

### 1.4 表间关系

| 主表 | 关联表 | 关系 | 关联字段 | 业务含义 |
|---|---|---|---|---|
| `mon_device` | `mon_device_credential` | 1:1 | `device_id` | 一台设备一套协议凭据 |
| `mon_device` | `asset_info` | 1:1（可空） | `asset_info.device_id` | 资产绑定监控设备，绑定后可看实时数据 |
| `mon_device` | `metric_latest` / `metric_sample` | 1:N | `device_id` | 一台设备多指标、多采样点 |
| `mon_device` | `alert_rule` | 1:N | `device_id`（NULL=全局规则） | 支持按设备定制阈值 |
| `metric_catalog` | `metric_latest`/`metric_sample`/`alert_rule` | 1:N | `metric_key` | 指标字典驱动，新增指标不改表 |
| `alert_rule` | `alert_rule_state` | 1:1 | `rule_id` + `device_id` | 连续计数器（防重启丢失） |
| `alert_rule` | `alert_event` | 1:N | `rule_id` | 一条规则产生多次告警事件 |
| `alert_event` | `alert_notify_record` | 1:N | `event_id` | 一次事件多渠道推送，逐条记录结果 |
| `asset_info` | `asset_maintain_remind` | 1:N | `asset_id` | 维保到期提醒 |

## 三、核心表字段设计

### 3.1 `mon_device` 监控设备（主表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK | 主键 |
| `name` | VARCHAR(128) | NOT NULL | 设备名称，大屏展示用 |
| `ip` | VARCHAR(64) | NOT NULL | 管理 IP，采集目标 |
| `device_type` | VARCHAR(32) | NOT NULL | `switch`/`server`/`firewall`/`router`/`storage` |
| `vendor` | VARCHAR(32) | | `huawei`/`h3c`/`cisco`/`windows`/`linux`/`kylin`/`uos`/`other` |
| `os_type` | VARCHAR(64) | | 操作系统明细，信创主机区分麒麟/统信用 |
| `protocol` | VARCHAR(16) | NOT NULL | `snmp`/`ssh`/`winrm`/`icmp`，决定走哪个采集器 |
| `model` | VARCHAR(64) | | 型号 |
| `location` | VARCHAR(128) | | 物理位置（机房/楼层/机柜） |
| `asset_id` | BIGINT | | 关联资产（冗余，双向可查） |
| `collect_interval` | INT | 默认 60 | **每台独立采集周期（秒）**，需求点：可单独配置 |
| `timeout` | INT | 默认 10 | 单次采集超时（秒），超时不影响其他设备 |
| `enabled` | TINYINT | 默认 1 | 启用/停用采集任务 |
| `online_status` | VARCHAR(16) | 默认 `unknown` | `online`/`offline`/`unknown`，由 Ping/采集结果更新 |
| `fail_count` | INT | 默认 0 | 连续失败次数，用于判定离线与异常设备 |
| `last_collect_at` | DATETIME | | 上次采集时间，调度器判断是否到点 |
| `last_online_at` | DATETIME | | 最后在线时间 |
| `remark` / `created_at` / `updated_at` | | | 通用字段 |

**索引**：`idx_device_ip`、`idx_device_enabled_proto`（调度器每轮扫描的过滤条件）。

### 3.2 `mon_device_credential` 设备协议凭据

一张表存四类协议凭据（按 `protocol` 各取所需字段），避免四张小表。

| 字段 | 说明 |
|---|---|
| `protocol` | `snmp`/`ssh`/`winrm`/`icmp` |
| `snmp_version` / `snmp_community` / `snmp_port` | v2c 用团体字 |
| `snmp_username` / `snmp_auth_proto` / `snmp_auth_key` / `snmp_priv_proto` / `snmp_priv_key` | v3 认证+加密（MD5/SHA、DES/AES） |
| `ssh_port` / `ssh_username` / `ssh_password` / `ssh_device_type` | `ssh_device_type` 直接对应 netmiko：`huawei`、`hp_comware`（华三）、`linux` |
| `winrm_port` / `winrm_username` / `winrm_password` / `winrm_transport` | `ntlm`/`basic`/`ssl` |
| `ping_count` / `ping_interval` / `ping_timeout` / `ping_size` | 长 Ping 参数：包数、间隔、超时、包大小 |

**安全设计**：`ssh_password`/`winrm_password`/`snmp_auth_key` 一律用 **Fernet 对称加密**后入库，密钥来自 `.env` 的 `SECRET_KEY`，数据库泄露也不明文暴露口令。字段加 `_enc` 后缀明示（见 SQL 文件）。

### 3.3 `asset_info` IT资产台账（需求模块 2）

| 字段 | 说明 |
|---|---|
| `asset_code` | 资产编号，**唯一**，支持导入去重 |
| `name` / `device_type` / `vendor` / `model` / `serial_no` | 基础信息 |
| `ip` / `mac` | 网络信息 |
| `room_location` / `rack_position` | 机房位置、机位 |
| `online_at` | 上架时间 |
| `warranty_start` / `warranty_end` | 维保起止，**大屏维保到期预警**依据 |
| `owner` / `owner_phone` | 责任人 |
| `supplier` / `purchase_at` / `purchase_price` | 采购信息 |
| `status` | `in_use`/`idle`/`repair`/`scrapped` |
| `device_id` | 绑定监控设备 → 资产详情页直接看实时监控数据 |

### 3.4 指标三表：字典 + 热 + 冷

**`metric_catalog` 指标字典**：`metric_key`（如 `cpu_usage`、`if_in_rate`）统一注册，带单位、类型（`gauge`/`counter`/`state`）、来源协议、是否内置。新增指标 = 加一行数据 + 写一个解析函数，**不改表结构**。

**`metric_latest` 热表**：
- 唯一键 `UNIQUE(device_id, metric_key)` → 支持 UPSERT（`ON CONFLICT` / MySQL `ON DUPLICATE KEY UPDATE`）。
- 行数 = 设备数 × 指标数（200 台 × 20 指标 = 4000 行），大屏聚合秒级返回。
- `str_value` 冗余列存字符串型指标（如设备版本、端口状态 up/down）。

**`metric_sample` 冷表**：只 INSERT 不 UPDATE，索引 `(device_id, metric_key, collect_time)` 支撑曲线查询。

**降采样清理策略（定时任务，见第 4 步）**

| 数据龄 | 处理 |
|---|---|
| ≤ 7 天 | 保留原始采样 |
| 7~30 天 | 聚合为 5 分钟粒度（平均值），删除原始行 |
| 30~90 天 | 聚合为 1 小时粒度 |
| > 90 天 | 删除 |

### 3.5 告警四表：规则 + 状态 + 事件 + 通知

**`alert_rule` 告警规则**

| 字段 | 说明 |
|---|---|
| `device_id` | 为 NULL 时表示**全局规则**（对同类设备批量生效） |
| `metric_key` | 绑定的指标键；`offline` 为特殊键表示设备离线告警 |
| `operator` / `threshold` | 比较符 `gt/lt/ge/le/eq/ne` + 阈值 |
| `duration_n` | **连续 N 次超标才触发**（需求：防抖动误报） |
| `recovery_n` | **连续 M 次正常才恢复**（滞回，防阈值边缘反复） |
| `level` | `critical`紧急 / `major`重要 / `minor`一般 / `info`提示 |
| `converge_window` / `converge_max` | 收敛窗口（秒）+ 窗口内最大推送条数（防消息轰炸） |
| `notify_channels` | JSON 数组：`["email","wecom","dingtalk","wechat"]` |
| `silence_until` | 静默截止时间（维护窗口期不发告警） |
| `enabled` | 启用/停用 |

**`alert_rule_state` 规则运行状态**：`breach_count`（连续超标计数）、`normal_count`（连续正常计数）、`status`、`last_value`、`current_event_id`。
> 为什么落库而不只放内存：平台重启后计数器不丢失，否则重启瞬间会造成一批重复告警。

**`alert_event` 告警事件**：`fingerprint = md5(device_id + rule_id)` 用于收敛；`occur_count` 累计同指纹触发次数；`status` 流转 `firing → acked → recovered/closed`；`ack_user`/`ack_at` 支撑"手动标记已确认"。

**`alert_notify_record` 通知记录**：每个渠道一条，记 `status`（success/fail）、`retry_count`、`response_msg`，推送失败可在页面重发。

### 3.6 日志与配置

- `sys_config`：`config_group` 分 `mail`/`wecom`/`dingtalk`/`wechat`/`collect`/`system` 六组，`is_secret=1` 的项（密钥、口令）在 API 返回时自动脱敏（`***`），前端只显示"已配置"。
- `collect_log`：每台每次采集一条，含 `duration_ms`、`status`、`error_msg`、`metric_count`，是"采集异常排查"和"设备采集成功率"统计的基础。
- `alarm_log`：告警全链路动作留痕 `trigger`/`recover`/`ack`/`notify`/`close`。

## 五、索引设计汇总

| 表 | 索引 | 用途 |
|---|---|---|
| `mon_device` | `(ip)`、`(enabled, protocol)`、`(online_status)` | 调度扫描、大屏在线统计 |
| `metric_latest` | `UNIQUE(device_id, metric_key)`、`(metric_key)` | UPSERT、按指标横向聚合 |
| `metric_sample` | `(device_id, metric_key, collect_time)`、`(collect_time)` | 曲线查询、按时间清理 |
| `alert_event` | `(fingerprint)`、`(status, level)`、`(last_occur_at)` | 收敛查重、告警中心筛选 |
| `alert_rule` | `(device_id, metric_key)`、`(enabled)` | 评估时快速取规则 |
| `asset_info` | `(asset_code)` UNIQUE、`(warranty_end)`、`(device_id)` | 导入去重、维保预警 |
| `collect_log` / `alarm_log` / `sys_log` | `(created_at)` | 按时间范围查日志 |

> `metric_sample` 是唯一可能到千万级的表：SQLite 下靠 `(device_id, metric_key, collect_time)` 复合索引 + 定期清理控制体积；迁移 MySQL 后可进一步按 `collect_time` 做分区。
