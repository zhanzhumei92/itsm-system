| 约束 | 落地方式 |

## 三、核心设计实现

### 3.1 双密码策略（`core/security.py`）

需求要求「后台管理含用户管理」，而设备采集又必须拿到明文口令，两者的密码学要求相反，因此分成两条独立通道：

| 用途 | 算法 | 可逆 | 字段标记 | 原因 |
|---|---|---|---|---|
| 登录密码 | bcrypt（rounds=12） | ✗ 不可逆 | `password_hash` | 只需校验，永远不需要还原明文 |
| 设备口令 / 告警密钥 | Fernet 对称加密 | ✓ 可逆 | `*_enc` 后缀 | 采集时必须以明文调协议库 |

**关键取舍**：未配置 `FERNET_KEY` 时 `encrypt_secret()` **直接抛错，绝不降级为明文存储**。静默降级会让「加密」变成一句空话，且故障在很久以后才暴露。

### 3.2 指标冷热分离（`services/metric_service.py`）

200 台设备 × 10 指标 × 每分钟一次 = 每天 288 万条。全部走一张表会让大屏查询越来越慢。

| 表 | 定位 | 写入方式 | 行数规模 |
|---|---|---|---|
| `metric_latest` | 热表，大屏实时读 | UPSERT（唯一键冲突则更新） | 恒定 = 设备数 × 指标数 |
| `metric_sample` | 冷表，历史曲线 | 只 INSERT | 随时间增长，靠降采样清理 |

**UPSERT 方言差异集中封装**：`_upsert_latest()` 是唯一处理 SQLite `on_conflict_do_update` / MySQL `on_duplicate_key_update` 的地方。迁 MySQL 只改 `.env` 里的 `DATABASE_URL`，业务代码零改动。

### 3.3 历史曲线自动降采样

查询跨度越大，原始点越多。`get_history()` 按时长自动选择粒度：

| 时间跨度 | 粒度 | 聚合方式 |
|---|---|---|
| ≤ 6 小时 | raw 原始点 | 直接查 |
| 6 ~ 72 小时 | 5 分钟 | 5 分钟分桶取平均 |
| > 72 小时 | 1 小时 | 1 小时分桶取平均 |

分桶在 **Python 侧聚合**（先按时间排序分组再算均值），而不是用 SQL 的 `strftime`/`DATE_FORMAT`——后者是 SQLite 与 MySQL 方言差异最大的地方，避开它才能保证零改造迁移。

### 3.4 采集并发模型（`tasks/executor.py`）

- `ThreadPoolExecutor(max_workers=60)`：采集全是网络 IO，GIL 在 IO 等待时释放，线程池足够；200 台 ÷ 60 ≈ 4 批，单轮远小于 60 秒采集周期。
- **防重入**：维护 `_running` 集合，同一设备上一轮未结束则跳过本轮，避免设备响应慢时任务堆积把线程池打满。
- **单台失败隔离**：每个采集任务独立 try/except，失败只写 `collect_log`，不影响同批其它设备。

### 3.5 采集器注册器模式（`collectors/base.py` + `factory.py`）

```python
@CollectorRegistry.register("snmp")   # 新增协议只需加这一行 + 实现类
class SnmpCollector(BaseCollector):
    ...
```

新增协议（如后续要加 Modbus 采集 UPS）**只新增文件，不改动任何既有代码**，符合需求中的低耦合扩展要求。

**容错导入**：`collectors/__init__.py` 用 `_OPTIONAL_MODULES` 列表逐个 try/import。第 4 步的采集器尚未交付时，日志只提示「采集器模块未加载」，平台照常启动——避免「一个协议库缺失导致整个平台起不来」。

### 3.6 统一响应与异常体系（`core/response.py` + `exceptions.py`）

响应结构固定：`{"code": 0, "msg": "成功", "data": {...}}`

**状态码划分原则**（本次收尾时统一，非常重要）：

| 类别 | HTTP | 业务码 | 典型场景 |
|---|---|---|---|
| 协议层/权限层错误 | **4xx** | 与状态码同值 | 401 未登录、403 无权限、404 资源不存在、400 参数不合法 |
| 业务规则不通过 | **200** | **1xxx** | 1001 数据重复、1004 操作被规则拒绝、1005 状态不允许、1006 文件不合法 |

**为什么这样分**：请求「被正确处理了」与「业务不允许」是两件事。若业务错误也返回 4xx，前端 axios 必须在 `catch` 分支里再解析 `body.code`，逻辑与正常分支重复。现在前端拦截器只需：

```js
if (status === 401) 跳登录页
if (status === 403) 提示无权限
else if (res.data.code !== 0) 弹窗 res.data.msg   // 其余业务错误全在这里
```

### 3.7 数据库兼容设计（`core/database.py`）

| 措施 | 目的 |
|---|---|
| `BigInteger().with_variant(Integer, "sqlite")` | SQLite 只有 `INTEGER PRIMARY KEY` 才自增，MySQL 需 BIGINT |
| 不使用物理外键 | 关联完整性由 Service 维护，保证 SQLite↔MySQL 零改造迁移 |
| `PRAGMA journal_mode=WAL` + `busy_timeout=5000` | 读写并发：采集写入不阻塞大屏读取 |
| PRAGMA 放在 `event.listens_for(engine, "connect")` | 连接池每条新连接都生效，而非只在第一条上生效 |
| `expire_on_commit=False` | commit 后对象仍可读，避免序列化时触发额外查询 |

## 四、★ 验证中发现并修复的问题

本次收尾验证不是「跑通就算」，而是逐接口按契约断言。共发现 **7 个真实缺陷**，全部已修复并复验。

### 问题 1（严重）：入参校验器污染输出路径，一条脏数据拖垮整个列表

**现象**：调用 `GET /api/v1/devices` 返回 500，报 `ValidationError: device_type 只能是 firewall/...`。

**根因**：`DeviceOut(DeviceBase)` 继承了基类上的 `field_validator`。Pydantic 在校验**输出**时同样会执行这些校验器。于是库中只要存在一条枚举外的历史数据（旧版本写入、手工改库、采集器自动发现的新型号），整个列表接口就崩。

**同一模式在 3 个模块中都存在**：

| 输出类 | 继承的校验器 |
|---|---|
| `DeviceOut(DeviceBase)` | `device_type`、`protocol`、`ip` |
| `AssetOut(AssetBase)` | `status` |
| `AlertRuleOut(AlertRuleBase)` | `operator`、`level`、`notify_channels` |

**其中资产模块还构成了完整故障链**：`AssetUpdate.status` 当时**没有任何校验** → PUT 一个中文「在用」能成功入库 → 再打开资产列表就 500。也就是「改错一个字段，整页打不开」。

**修复**：
1. 抽出 `_DeviceInputValidators` / `_AssetInputValidators` / `_AlertRuleInputValidators` 三个校验器集合，由 **Create/Update 类**继承；
2. 三个 `*Out` 类改为**独立声明字段**，不继承带校验器的基类；
3. 输出侧对未知取值**原样透出**（`DEVICE_TYPE_TEXT.get(x, x)`），字段类型放宽为 `Optional`——即便库里是 NULL 也不影响其它记录正常返回。

**新增回归测试**（已固化到验证脚本）：直接向数据库写入 `device_type='legacy_type'`、`status='archived'`、`operator='gte'` 等枚举外数据，确认三个列表接口仍返回 200 且原样透出。

### 问题 2（严重）：编辑设备时「凭据留空保持不变」被校验拦死

**现象**：只想改设备名，提交 `credential: {protocol: "snmp"}` 返回 400「SNMP v2c 必须填写团体字」。

**根因**：`CredentialIn` 的 `@model_validator` 要求按协议填写必填项——这对**新增**是对的，但**编辑**场景的语义是「敏感项留空 = 保持原密文不变」。运维改个设备名不可能每次重输一遍口令。

**修复**：新增 `CredentialPatchIn(CredentialIn)`，重写同名 `model_validator` 跳过完整性校验（父类 validator 被子类同名方法覆盖）。`protocol` 取值本身的合法性仍然校验。`DeviceUpdate.credential` 改用该类。

**验证**：改设备名后重新查询详情，`has_snmp_community=True`，确认原密文未被清空。

### 问题 3：三个 Update 入参完全没有校验（问题 1 的「入口」）

`AssetUpdate`、`AlertRuleUpdate`、`DeviceUpdate` 此前均无 `field_validator`，可以把任意字符串写进 `status`/`operator`/`level`/`device_type`。这是问题 1 故障链的上游。

**修复**：三者分别继承对应的入参校验器集合。写入口是最后一道防线，即使输出侧已宽松化，也不允许脏数据进来。

### 问题 4：`/api/v1/users` 返回 404

**根因**：`app/api/router.py` 的 import 与 `include_router` 都漏掉了 `users` 模块（用户管理整个模块未接入）。

**修复**：补上 import 与注册。同时把路由注册顺序纳入检查脚本。

### 问题 5：业务异常未统一使用业务码

`DuplicateException` 是 `HTTP 200 + code 1001`（符合约定），但「内置 admin 不允许删除」「内置指标不允许删除」这类**同样是业务规则拒绝**的错误却抛裸 `BizException` → HTTP 400。前端需要为语义相同的两类错误写两套判断。

**修复**：
- 新增业务码 `1004`（操作被拒绝）、`1005`（状态不允许）、`1006`（文件不合法）；
- 新增异常类 `OperationDeniedException`、`StateInvalidException`、`FileInvalidException`；
- 逐处按语义归位（共 13 处）；
- 顶部的状态码划分原则写成表格文档，避免后续再次走偏。

**刻意保留为 HTTP 400 的 7 处**：参数长度、时间倒置、协议不一致、原密码错误等——这些确实属于「请求内容有问题」，用户需要改的是输入内容。

### 问题 6：`StateInvalidException` 定义正确但未生效

**现象**：对已恢复的告警再次确认，返回 `HTTP 400 code=400`，期望 `HTTP 200 code=1005`。

**根因**：修复过程中的操作失误——`alert_service.py` 的两处修改（import 与 raise）实际未落地，仍是旧的 `raise BizException(...)`。异常类本身定义正确（实测 `code=1005 / http_status=200`）。

**排查手段**：写了 AST 静态检查脚本，扫描全部 `raise XxxException(` 位置并比对该文件是否已导入该类。该脚本当场还揪出 `assets.py`、`metric_service.py` 两处同类遗漏。

**教训**：对同一文件的多处修改必须**串行执行并逐步复核**，不能只依赖编辑成功的返回。

### 问题 7：设备类型枚举过窄，无法纳管安防/弱电设备

原枚举仅 `switch/server/firewall/router/storage`。而本项目面向政企弱电集成，接的是海康门禁、摄像头、无线 AP、UPS。演示数据里门禁控制器只能写成 `other`，而 `other` 当时又不在合法枚举中——这正是问题 1 的触发点。

**修复**：扩展为 10 类并补齐中文名，同时保留 `other` 兜底：

`switch` 交换机 / `router` 路由器 / `firewall` 防火墙 / `server` 服务器 / `storage` 存储设备 / `camera` 视频监控设备 / `access` 门禁设备 / `ap` 无线AP / `ups` UPS 电源 / `other` 其他设备

**没有 `other` 兜底值，集成项目里的非标设备（环境监测仪、广播主机）就永远录不进平台。**

### 其他清理

- 用 pyflakes 全量扫描，清理 11 处 unused import，**静态检查从「13 条告警」到「零输出」**；
- 修正 `AssetOut` 的 4 个时间字段：原来继承 `AssetBase` 时是裸 `datetime`，会输出 ISO 8601 格式，与项目「统一输出 `YYYY-MM-DD HH:MM:SS`」的约定冲突，改为 `OptionalDateTimeStr`；
- `AlertRuleOut.notify_channels` 增加 JSON 字符串兜底解析（库里存的是 `'["email"]'`）。

### 6.1 端到端用例（95 项，全部通过）

按真实 HTTP 契约逐接口断言状态码与业务码，覆盖「增 → 查 → 改 → 删」全链路，不只是 GET：

| 分组 | 项数 | 覆盖内容 |
|---|---|---|
| 认证与权限 | 7 | 登录成功/失败、无令牌 401、viewer 越权 403 |
| 用户管理 | 11 | CRUD、重复账号 1001、密码长度 400、内置 admin 三重保护 1004 |

## 七、需要你确认的设计决策

以下几项是本次实现中我做出的判断，如果你有不同意见，现在改动成本最低：

| # | 决策 | 我的理由 |
|---|---|---|
| 1 | **业务规则类错误统一返回 HTTP 200 + 1xxx 业务码**，仅 401/403 保留真实状态码 | 前端拦截器只需一套逻辑。若你更倾向 RESTful 语义（业务错误也用 4xx），改动只涉及 `exceptions.py` 一个文件 |
| 2 | **不使用物理外键**，关联完整性由 Service 保证 | 保证 SQLite→MySQL 零改造迁移。代价是绕过接口直接删数据可能留下孤儿记录 |
| 3 | **设备类型扩展为 10 类**（含门禁/摄像头/AP/UPS/其他） | 面向弱电集成场景必须能纳管安防设备 |
| 4 | **输出侧不做枚举强校验**，未知取值原样透出 | 一条脏数据不应让整页 500。前端按字典渲染，未命中显示原值 |
| 5 | **采集用「固定 tick + 数据库筛选到点设备」**，而非每设备一个调度 job | 200 台设备只占 1 个调度任务；新增设备无需重建调度器 |
| 6 | 实时值用 **UPSERT 热表**，历史值用**只 INSERT 冷表** | 大屏查询行数恒定，不受历史数据量影响 |
| 7 | **重复确认「已确认」的告警算幂等成功**（允许改备注），只有已恢复/已关闭才拒（1005） | 值班交接场景需要补/改备注。副作用是会覆盖 `ack_at`/`ack_user`，但 `alarm_log` 保留了每次操作的时间线。若你要求「首次确认时间不可变」，我改成 `ack_at` 只在为空时写入 |

> 验证套件里这两条分支现在都有专门用例守着：`重复确认(幂等)` 与 `已恢复告警再确认→1005`。
