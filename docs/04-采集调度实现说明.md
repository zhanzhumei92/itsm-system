## 二、采集调度：三个关键取舍

### 2.1 「固定 tick + 库里筛到点设备」，而不是每台设备一个调度任务

需求是"200 台设备并发采集、支持每台设备独立周期"。最直觉的做法是给每台设备
在 APScheduler 里注册一个 job，但那样会有三个问题：

| 方案 | 新增设备 | 改采集周期 | 调度器压力 |
|------|----------|------------|------------|
| 每设备一个 job | 必须重建调度器（运行期改不动） | 删旧 job 建新 job，易漏 | 200+ 个 job 的触发队列 |
| **固定 tick + 库里筛（采用）** | 无需任何操作，下一轮自动纳入 | 改数据库字段即可 | 恒定 1 个 job |

代价是每个 tick 要扫一遍设备表。这个代价被压到最小的做法是：
**只 select 三列**（id / collect_interval / last_collect_at），
在 Python 里做时间比对，而把真正的网络 IO 全部丢给线程池。

> 为什么不在 SQL 里做时间加法：`last_collect_at + collect_interval <= now`
> 在 SQLite 是 `datetime(col, '+' || n || ' seconds')`、在 MySQL 是
> `DATE_ADD(..., INTERVAL n SECOND)`，两套方言不通用；且 SQLite 里 datetime
> 存的是字符串，这个表达式用不上索引，反而比"取回 200 行内存比对"更慢。
> **换方言无关性，牺牲可忽略的开销** —— 这是本项目"SQLite 初期、MySQL 无缝迁移"
> 目标下的标准取舍。

### 2.2 「汇总任务」触发告警评估，而不是独立的告警定时任务

告警评估必须读到"本轮刚写入的指标"，且同一台设备在同一轮内只能评估一次。
如果做成独立的定时任务，它无从知道"本批采集写完没有"，会出现两种错误：
读到上一轮的旧值，或者同一批数据被评估两次。

因此采集任务在投递完设备任务后，**再投递一个汇总任务**，它 `wait()` 等本批
future 全部结束后才执行评估。这天然保证了上面两条约束。

等待用 `wait(timeout=120)` 而不是逐台 `result()`：逐台 `result()` 会在第一台卡住
的设备上阻塞到底；`wait()` 能在总预算耗尽时立刻返回，让已完成设备的数据及时进入
评估。未完成的设备下一轮正常纳入，只是这一轮不参与评估 —— **超时不是错误**。

### 2.3 单设备失败隔离

每台设备的采集跑在**独立 Session、独立 try/except** 中（`_collect_one_device`）：

- 采集器内部已兜底（不抛异常），调度器这里是第二道防线；
- 数据库写失败只影响这一台，事务回滚不波及其它设备；
- 无论成败都写 `collect_log`，保证"为什么没数据"可追溯。

一个刻意的例外：**协议不支持时不累加 `fail_count`**。这属于配置问题而非设备故障，
若累加会把设备误判为离线，让现场排查方向彻底跑偏（去查网络，其实是用错了协议）。

## 三、四个采集器的实现要点

### 3.1 SNMP（`snmp.py`）— 厂商私有 OID 优先，标准 MIB 兜底

| 指标 | 厂商私有 OID（优先） | 标准 MIB（兜底） |
|------|---------------------|------------------|
| CPU | huawei / h3c / cisco 各自的私有 OID | `hrProcessorLoad` |
| 内存 | 厂商已用/总量 OID | `hrStorageTable`（按 descr 关键字匹配） |
| 温度 | 厂商私有 OID（标准 MIB 无） | 无（返回空值） |

**为什么优先私有 OID**：标准 `hrProcessorLoad` 在不少交换机上整机只返回一个
"平均负载"值，而私有 OID 能拿到**每块业务板**的 CPU。多行取**最大值**而非平均值 ——
一块板卡跑满就是真故障，取平均会被其它空闲板卡拉平，把故障掩盖掉。

端口速率需要两次采样做差，且必须处理计数器回绕：

```python
delta = curr - prev
if delta < 0:                       # 64 位计数器回绕
    wrapped = delta + 2**64
    if wrapped / elapsed / 1e6 * 8 > 1_000_000:   # >1000Gbps，只能是设备重启
        return None                 # 放弃本轮，等下一轮重新建立基线
```

另外做了两件容易被忽略的事：**接口按数值排序**（1,10,11,2 → 1,2,10,11），
避免裁剪 48 口时把大编号端口砍掉；**凭据前置校验**，不合格直接返回，
省掉 5 秒的超时等待。

### 3.2 SSH（`ssh.py`）— 延迟导入 + 绝不让会话泄漏

- **netmiko 函数内延迟导入**：若在模块顶部 import，Python 3.13 移除 `telnetlib`
  后 netmiko 4.3.0 会直接 ImportError，导致**整个 ssh 协议不注册**，
  用户看到的是"暂不支持的采集协议：ssh"，被彻底带偏。现在顶层导入失败
  只影响 SSH，其它协议照常工作。
- **`finally: connection.disconnect()`**：华为设备默认只有 5 个 vty 会话，
  会话泄漏几轮后所有 SSH 都连不上，且现象是"设备突然全部离线"，极难定位。
- **`fast_cli=False`**：华为/华三老固件与信创 shell 的提示符识别容易出错，
  用可靠性换一点速度是值得的。
- 异常日志只取 `type(exc).__name__` + 首行前 200 字符，**防止口令泄漏到日志**。

### 3.3 WinRM（`winrm.py`）— 用 PowerShell + CIM，而不是 WMI 包

`wmi` 包依赖 `pythoncom`，只能在 Windows 采集机上运行；而本平台定位是
"Linux 服务器也能管 Windows 设备"。改用 `pywinrm` 执行 PowerShell、
内部调 `Get-CimInstance`（WMI 的继任者），跨平台一致。

输出格式刻意用 `KEY=VALUE` 单行文本而非 JSON：PowerShell 各版本对单元素数组的
JSON 序列化行为不一致（有时对象、有时字符串），`ConvertTo-Json` 在 5.1 与 7.x
上还有转义差异。`KEY=VALUE` 加分隔符解析简单且稳定。

中文 Windows 返回的是 GBK 字节，因此做了**级联解码**：
`utf-8 → gbk → gb18030 → utf-16-le → latin-1`，保证"计算机名/服务显示名"
不乱码。

### 3.4 ICMP（`icmp.py`）— 两级探测自动降级（本步最重要的一处修正）

`requirements.txt` 原先写"pythonping 无需 root 权限"，**这是错的**：
pythonping 走 `SOCK_RAW`，Linux/macOS 需要 root 或 `CAP_NET_RAW`，Windows 需要管理员。

实测证据（第 4 步真机验证）：

```
PermissionError: [Errno 1] Operation not permitted
```

这不是沙箱特例，而是产品级事实。因此实现**两级探测**：

1. 优先用 pythonping（微秒级精度）；
2. 一旦遇到权限错误，进程级记住并**自动降级为调用系统 `ping` 命令**，
   只告警一次（不刷日志）。

系统 ping 的平台差异也被处理好：Linux `-W` 单位是**秒**、macOS 是**毫秒**、
Windows 用 `-n/-w/-l`；解析兼容中文 Windows 的
`已发送/已接收/丢失`、`最短/最长/平均`。

另一个设计点：**设备不可达算"采集成功"**。因为我们成功探测到了"它离线"这个事实；
离线由 `online_status` 表达、由告警引擎处理。若记成采集失败，日志里就再也分不清
"网络不通"与"SNMP 团体字配错了"。

抖动用**标准差**而非极差：极差对单个离群点过于敏感。

## 四、解析器层：厂商差异全部在解析器里消化

注册器模式，新增厂商不改任何既有代码：

```python
@ParserRegistry.register("huawei_vrp")
class HuaweiVrpParser(BaseCommandParser):
    CMD_VERSION = "display version"
    ...
```

三个解析器里几处"看起来多此一举、其实必须"的处理：

| 处理 | 原因 |
|------|------|
| 兼容华为固件真实错别字 `Devic[ed]\s+S/?N` | 现场确实存在把 `Device` 打成 `Devicd` 的固件版本 |
| 华三 CPU 取"1 分钟"窗口 | 5 秒抖动大、5 分钟太迟钝，1 分钟是行业标准 |
| Linux CPU 读 `/proc/stat` 两次采样做差 | 单次读只能得到累计 jiffies，必须做差才是使用率 |
| `iowait` 计入空闲 | 与 `top`/`sar` 口径一致，否则运维一看平台就质疑数字对不上 |
| 内存优先 `MemAvailable` | 用 `MemFree` 会把页缓存算作已用，永远显示 90%+ 假告警 |
| 磁盘 `df -kP` 排除 tmpfs/overlay 并按设备去重 | 容器环境里同一块盘会被 bind mount 多次，不去重会重复统计 |
| 版本串保留 `Release 6555P01` 补丁号 | 现场判断"要不要升级"靠的就是补丁号 |
| 复合命令用 `@@@SPLIT@@@` 分段 | 用空行/提示符切分会被命令自身的空行误导，导致字段错位 |

**不从华为 `display interface brief` 取端口流量**：那一列是 `InUti/OutUti`
带宽利用率百分比，而 `if_in_rate` 的语义是 Mbps，量纲不同。混用会让大屏
TOP 排行出现"利用率 30%"和"流量 300Mbps"两种数字没法比。故该命令只产出
`if_status` 与 `if_util`，端口流量交给 SNMP。

## 五、本步发现并修复的问题

### 问题 1（严重）：ORM 元数据缺失两个复合唯一索引，与 SQL 建表脚本不一致

**现象**：新增的 `tests/test_collect_job.py` 一跑就炸：

```
sqlalchemy.exc.OperationalError: ON CONFLICT clause does not match any
PRIMARY KEY or UNIQUE constraint
[SQL: INSERT INTO metric_latest (...) ON CONFLICT (device_id, metric_key) DO UPDATE ...]
```

**根因**：同一张表存在**两处定义**——手写的 `sql/schema_sqlite.sql` 与 ORM 模型，
二者漂移了：

| 表 | SQL 脚本 | ORM 模型（修复前） |
|----|----------|-------------------|
| `metric_latest` | `CREATE UNIQUE INDEX uk_latest_device_metric ON metric_latest(device_id, metric_key)` | **无** |
| `alert_rule_state` | `CREATE UNIQUE INDEX uk_rule_state ON alert_rule_state(rule_id, device_id)` | **无** |

**为什么这是严重问题**（两种数据库的表现完全不同）：

- **SQLite**：直接报 `ON CONFLICT clause does not match ...`，问题暴露在明处；
- **MySQL**：`ON DUPLICATE KEY UPDATE` 在**没有唯一键时不报错**，退化为普通
  `INSERT`。于是 `metric_latest` 每轮采集新增一批行，
  "表体积恒定 = 设备数 × 指标数" 的设计保证被**静默打破**，
  直到大屏变慢、磁盘写满才被发现。
- `alert_rule_state` 更直接：`get_rule_state()` 用的是 `scalar_one_or_none()`，
  同一 (规则, 设备) 出现多行就会抛 `MultipleResultsFound`，**让整批告警评估中断**
  —— 而这正好是第 5 步要用的方法。

**修复**：在两个模型的 `__table_args__` 里显式声明索引，索引名与 SQL 脚本严格同名，
保证"ORM 建表（`create_all`）"与"SQL 脚本建表"两条路径产出完全一致的结构。

**为什么之前没发现**：生产库是用 `sql/schema_sqlite.sql` 建的（所以索引存在、
采集一直正常），而 `init_db()` 的 ORM 路径只在"调试/单测/MySQL 初始化"时走。
测试用例第一次覆盖到这条路径，就把它暴露出来了 —— 这正是"临时脚本必须固化成
正式用例"的价值。

### 问题 2：静态自检新增检查 5 —— 并顺带修掉检查器自身的一个缺陷

为防止这类"两处定义漂移"再犯，`scripts/static_audit.py` 新增：

```
【检查 5】ORM 唯一约束 与 schema_sqlite.sql 保持一致
```

**第一次实现是错的**：它只做单向差集（"SQL 有、ORM 没有"）。
我用人为缺陷验证时发现——把 SQL 里的 `uk_latest_device_metric` 删掉后，
检查器**仍然报 OK**。反向同样致命：ORM 有而 SQL 没有，用 SQL 脚本建库的现场
一样缺这个索引。改为**双向比对**后复验：

```
【检查 5】ORM 唯一约束 与 schema_broken.sql 保持一致
  [FAIL] 表 metric_latest 的唯一约束 (device_id, metric_key) 只在 ORM 里，SQL 脚本缺失
  [FAIL] 表 metric_catalog 的唯一约束 (metric_key) 只在 ORM 里，SQL 脚本缺失
合计发现 2 个问题（需要修复）      退出码=1
```

真实脚本则干净通过。**检查器本身也必须被人为缺陷验证过**，否则等于摆设 ——
"一个从不报警的检查器"和"没有检查器"在效果上完全一样，但前者会带来虚假的安全感。

### 问题 3：回归套件覆盖度随运行次数衰减（套件自身的缺陷）

**现象**：`scripts/verify_api.py` 通过项从最初记录的 95 项变成了 90 项，失败数始终为 0。

**根因**：脚本原先是"从演示数据里挑一条 `firing` 事件来测详情/确认/时间线"，
而"确认告警"这一步会把事件从 `firing` 改成 `acked`，且这个变更是**产品设计上
不可逆的**。于是：

| 运行次数 | firing 事件 | 实际执行的用例 | 报告 |
|----------|-------------|----------------|------|
| 第 1 次 | 有 | 95 项 | 通过 95，失败 0 |
| 第 2 次起 | 无（已被上次自己改掉） | 89+1 项 | **通过 90，失败 0** |

**为什么这比"没有测试"更危险**：失败数一直是 0，报告永远是绿色的，
但整整 6 项接口契约实际上从第二次运行起就再没被执行过。任何人看到"通过 90，失败 0"
都只会认为一切正常。

**修复**：让用例**自给自足**，不依赖任何残留数据：

1. 告警段开始时，通过 service 层自备一条 `firing` 事件
   （产品刻意**不提供**"创建告警中事件"的接口 —— 告警只能由评估器产生，
   所以只能用测试夹具直接落库，性质等同工装夹具）；
2. 1005「当前状态不允许该操作」分支改为走**纯 HTTP** 路径验证：
   用 `close=true` 把事件关闭（确认误报），再对其发确认请求，必须被拒。
   不再依赖"演示数据里恰好有已恢复事件"；
3. 清理阶段显式删除自备事件及其 `alarm_log`
   （`delete_rule` 只清理 `alert_rule_state`，**刻意保留告警事件**供审计，
   所以必须自己删，否则每跑一次就多留一条残留）。

**复验**（连续三次运行）：

```
第 1 次：通过 98 项，失败 0 项
第 2 次：通过 98 项，失败 0 项
第 3 次：通过 98 项，失败 0 项
alarm_log 运行前=7 运行后=7      ← 零残留
alert_event: acked=4, recovered=1  ← 与运行前一致
```

覆盖度不再衰减，且通过项从 90 提升到 98（补回了被静默跳过的用例，
并新增了"关闭告警"与"自备事件已清理"两项）。

### 其他清理

- 修掉 pyflakes 报出的 6 处未使用导入 / 无用赋值 / 空 f-string。
- `requirements.txt` 修正两处事实错误：
  - `netmiko==4.7.0`（4.3.0 在 Python 3.13 上因 `telnetlib` 被移除而无法导入）；
  - 删除"pythonping 无需 root 权限"的错误注释，改为说明其需要特权并已实现降级。

### 6.2 端到端真机验证（采集链路）

ICMP 降级链路（本机，无需特权）：

```
127.0.0.1     → online  / latency 0.11ms / loss 0%   / 探测方式=system_ping
```

## 七、需要你确认的设计决策（第 4 步新增 4 项）

| # | 决策 | 说明 | 备选 |
|---|------|------|------|
| 1 | SSH 采集默认 `fast_cli=False` | 用可靠性换速度，华为/华三老固件识别提示符更稳 | 若现场设备固件较新且要求吞吐，可改为按设备配置 |
| 2 | 单设备采集周期下限 **30 秒** | 防止有人填 1 秒把设备采挂（网络设备 SNMP 轮询的行业下限） | 可放宽，但不建议低于 15 秒 |
| 3 | 协议不支持时**不**累加失败次数 | 归为配置问题，避免把设备误判离线 | 若希望"配置错误也告警"，可在第 5 步加一条"采集配置异常"规则 |
| 4 | 端口流量只走 SNMP，SSH 只取状态与利用率 | 避免百分比与 Mbps 两种量纲混入同一指标键 | 若某型号 SNMP 不可用，可为其单独扩展 SSH 流量解析器 |
